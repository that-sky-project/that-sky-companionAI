# that-sky-companionAI

小光的桌面客户端，将大模型对话、光遇协议通信和本地地图导航接在一起。聊天、动作执行和移动控制各自独立：模型负责理解请求，客户端负责维护游戏状态并执行动作。

## 实现方式

### 桌面与后台

桌面窗口使用 pywebview，Windows 下由 WebView2 显示界面。`desktop.py` 启动本机 Python 后台，界面通过本地控制接口管理配置、资源生成和运行状态。桌面版与浏览器面板使用同一套后台逻辑。

地图计算放在独立的 Node.js 进程中，Python 通过 JSONL 消息调用它，避免把寻路和碰撞计算塞进聊天处理流程。

### 聊天与动作

默认只响应 `/` 开头的消息。不带 `/` 的可见聊天会作为近期背景记录，并保留说话人和房间信息，供后续对话使用。

带人换图、明确互动指令和游戏状态查询优先走本地规则；需要语义识别的请求再交给模型处理。模型适配层支持 OpenAI 兼容接口和 Anthropic Messages，返回的工具调用交给本地处理函数，不把模型文本直接当作游戏数据包发送。例如：

```text
/跟我走
/过来抱抱
/一起跳个转圈舞吧
/带我去云野大厅
```

互动动作、别名和等级由动作目录统一解析，自然语言互动请求还会绑定当轮说话人和文本。人设与近期聊天用于生成回复，不直接代替动作状态判断。

### 房间同步与交互

运行器维护游戏连接，房间跟踪器通过 PlayerSync 建立玩家编号映射，从 Game3 快照更新位置。跟随与姿态控制在本地运行，不需要模型逐帧决定角色怎么移动。

牵手、背背、拥抱和舞蹈等互动按邀请、接受、取消及状态回执推进。动作发起后，仍以实际同步状态为准。

带人切图先解析目的地，再通过可靠 ChangeLevel RPC 提交换图请求，随后衔接地图会话和新房间的牵手关系，不是直接改地图编号或坐标。

### 地形与移动

资源工具从 APK 中读取 `BstBaked.meshes` 等网格和场景配置，整理坐标变换与场景实例，生成本地使用的碰撞几何和导航数据。

- Recast/Detour 负责导航网格和路径查询。
- Rapier 负责碰撞、地面高度查询和角色移动约束。
- 跟随模块根据目标位置更新移动计划，并与跳跃、下落、拍翼等运动逻辑配合。

这些计算用于驱动角色的位置和动作同步，并不是运行原版客户端的完整物理引擎。地图数据由本机生成，仓库不附带游戏 APK 或提取后的地图资源。

## 验证与登录

客户端账号与网易游戏账号分开处理。客户端通过 HTTPS 对接独立服务，完成身份验证、游戏登录、安全验证、会话获取和续期请求。登录实现、账号库及长期续期逻辑不在本仓库中。

**有一定基础能力者可自行搭建验证登录系统。** 对接入口在 `app/xg_auth_client.py`、`app/xg_service_identity.py` 和 `app/bot/account_login.py`。自建时按这些适配层的请求与返回结构实现服务端，再配置对应的服务地址。

## 代码入口

- `desktop.py`：桌面宿主与本地后台的启动、退出。
- `app/bot/`：聊天处理、动作调度、跟随和切图。
- `app/qfsky/`：游戏协议通信及相关适配。
- `app/engine/`：导航、碰撞和运动计算。
- `app/xg_gamedata/`：APK 解析、场景整理和地形构建。
- `app/launcher/`：安装向导、采集与进程管理。

## 运行与开发

源码构建、运行时准备和地图生成见 [SOURCE_BUILD.md](SOURCE_BUILD.md)。Windows 桌面端需要 WebView2；Python 与 Node.js 的依赖分别由仓库中的 requirements 和 package-lock 文件管理。

在装好 Python 依赖后，可运行离线检查：

```sh
python -B -m unittest discover -s tests -v
```

运行产生的账号缓存、会话、日志和个人配置留在本机，不随源码分发。
